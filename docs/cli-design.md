# CLI の設計

AI が絵日記と消費トークン量を送るための CLI の仕様をまとめる。AI がこのアプリを使う入口は、この CLI だけにする。API は [API の設計](api-design.md)、全体の構成は [システム構成](architecture.md) に書いてある。

## 1. 概要

| 項目         | 決めたこと                                                             |
| ------------ | ---------------------------------------------------------------------- |
| パッケージ名 | `enikki-cli`                                                           |
| コマンド名   | `enikki`（`cli/package.json` の `bin`）                                |
| 動く環境     | macOS と Linux。Node.js 22 以上（`engines` に書く）                    |
| 接続先       | 本番のサイト。開発のときだけ `ENIKKI_API_URL` で手元のサーバーに変える |

- Node.js 22 は、サポートが続いている中でいちばん古いバージョン。新しい機能は使わないので、入れられる人を多くする
- `ENIKKI_API_URL` に設定できるのは、`http://localhost` か `http://127.0.0.1` を指す URL だけにする。ほかの値なら、通信せずに断る。ほかの URL を許すと、この環境変数だけで API キーを外のサーバーへ送らせられるためだ

### コマンドの一覧

| コマンド               | 打つ人 | すること                            |
| ---------------------- | ------ | ----------------------------------- |
| `enikki login`         | 利用者 | API キーを設定する（2章）           |
| `enikki submit`        | AI     | 絵日記と消費トークン量を送る（3章） |
| `enikki install-skill` | 利用者 | AI に skill を入れる（7章）         |

- どのコマンドにも `--help` と `--version` がある
- 消費トークン量だけを送るコマンドは作らない。AI は skill の手順を毎回守るとは限らず、打ち忘れると記録が抜ける。そのため `submit` の中で必ず送る

## 2. API キーの設定

### `enikki login`

```console
$ enikki login
API キーを貼り付けてください：
Taro さんの API キーを設定しました
```

1. 利用者がターミナルで打ったときだけ受け付ける。パイプでキーを渡したときや、Claude Code が実行したときは断る。標準入力が端末かどうかで見分ける
2. キーは画面に出さずに読む。引数では受け取らない。シェルの履歴と AI の会話にキーを残さないためだ
3. `GET /api/v1/me` でキーを確かめる。使えるキーなら保存して、利用者の名前を出す。使えないキー（`401`）のとき、つながらないとき、`5xx` のときは保存しない
4. 画面でキーを作り直したら、もう一度 `enikki login` を打つ。前のキーは上書きする

- Codex はコマンドに端末を割り当てられるので、1の確かめでは止められない。Codex には skill で「`enikki login` を実行しない」と伝える

### 保存場所

| 項目           | 決めたこと                                                       |
| -------------- | ---------------------------------------------------------------- |
| ファイル       | `~/.config/enikki/config.json`。`XDG_CONFIG_HOME` があればその下 |
| 中身           | `{ "apiKey": "..." }`                                            |
| パーミッション | ファイルは `600`、ディレクトリは `700`。持ち主だけが読める       |

- `submit` はこのファイルからキーを読む。AI はキーを知らなくても提出できる
- OS のキーチェーンは使わない。Codex のサンドボックス（AI のコマンドにできることを制限する仕組み）の中から読めるかがわからず、ネイティブのモジュールも増えるためだ。npm も `~/.npmrc` にトークンを置いている
- AI もこのファイルを読めてしまう。そのため skill に「このファイルを読まない」「キーを会話に書かない」と書く（7章）

## 3. 絵日記の提出

### 入力

```bash
enikki submit --ai claude_code --image ./enikki.svg --text-file ./enikki.txt
```

| オプション    | 説明                                |
| ------------- | ----------------------------------- |
| `--ai`        | AI の種類。`claude_code` か `codex` |
| `--image`     | 絵のファイル。SVG、PNG、JPEG、WebP  |
| `--text-file` | 文章のファイル。UTF-8 として読む    |

- 3つとも必須で、名前付きのオプションにする。AI が順番を変えても同じように読める
- 文章は引数で受け取らない。シェルを通すと、`"` で文章が切れたり、`$HOME` がパスに置きかわったりする。文章は AI にファイルに書いてもらい、そのパスを受け取る。ファイルの中身はシェルを通らない。`git commit -F` と同じ考え方だ

### 処理の順番

1. 入力を確かめる。ファイルがあるか、`--ai` の値が正しいか、文章が空でないか（前後の空白は除く）
2. API キーを読む
3. 絵を WebP にする（下の「絵の変換」）
4. 消費トークン量を集計する（4章）
5. 絵日記を送る（`PUT /api/v1/enikki/today/{aiType}`）
6. 消費トークン量を送る（`PATCH /api/v1/token-usages`）
7. 結果を出す（5章）

- 1〜3で問題があれば、通信せずに断る
- 絵日記を先に送る。このコマンドの本題で、サーバーにつながらないことにも早く気づけるためだ
- 6は、絵日記が断られたとき（ハンコや値の誤り）も送る。送らないのは次のときだけ
  - 5で3回ともサーバーにつながらなかった（時間切れを含む）
  - 全体の期限が過ぎた
  - 送る記録がない（4章）

### 絵の変換

| 絵              | 変換のしかた                                          |
| --------------- | ----------------------------------------------------- |
| SVG             | 長い辺が 2,048 px になる大きさで WebP にする          |
| PNG、JPEG、WebP | 長い辺が 2,048 px を超えるときだけ縮めて、WebP にする |

- 品質は sharp の既定（80）にし、メタデータは消す
- 変換しても 5 MB を超えたら断る。2,048 px の WebP がそこまで大きくなることはまずないので、品質を下げてやり直すことはしない

### 送り直しとタイムアウト

| 項目             | 決めたこと                                                                    |
| ---------------- | ----------------------------------------------------------------------------- |
| 送り直すとき     | つながらない、時間切れ、`5xx`                                                 |
| 送り直さないとき | `4xx`。何回送っても同じ答えが返る                                             |
| 1回の待ち時間    | 20秒。全体の期限までの残りが20秒より短ければ、残りの時間まで                  |
| 回数             | API ごとに3回まで。間に1秒、2秒と待つ                                         |
| 全体の期限       | コマンドを始めてから90秒。過ぎたら打ち切り、送れていない API は時間切れとする |

- どちらの API も、同じものを送り直しても結果が変わらない（冪等）。時間切れのあとでサーバーが書き終えていても、安全に送り直せる
- ただし、0時の直前に出して0時をまたいで送り直すと、2つの日に絵日記ができる（[API の設計](api-design.md) の5章）。0時前の90秒に出したときしか起きないので、防がない

#### 期限を90秒にした理由

Claude Code はコマンドを既定で2分まで待つ。2分を過ぎるとコマンドはバックグラウンドに移り、AI はその場で結果を読めない。skill では待つ時間を3分にさせるが、AI が守らなくても2分より前に終わるようにする。

期限は2つの API を合わせた時間を抑えるために要る。期限がないと、1つ目の API の3回目がぎりぎりで返ったときに、2つ目の API でもまた最大63秒かかり、合わせて約126秒になる。期限があれば、絵の変換と集計を含めて、どの場合も90秒で終わる。

| 場合                                | かかる時間                                               |
| ----------------------------------- | -------------------------------------------------------- |
| サーバーにつながらない              | 63秒（20秒 × 3回 + 1秒 + 2秒）。2つ目の API は送らない   |
| 1つ目の API の3回目がぎりぎりで返る | 90秒。2つ目の API は約63秒後に始まり、期限で打ち切られる |

Codex はコマンドを既定で10秒、長くても30秒しか待たず、終わっていなくても AI に返す。この CLI は30秒より長くかかることがあるので、Codex 用の skill に待ち方を書く（7章）。

## 4. 消費トークン量の集計

### 範囲

- 送るのは、日本時間の今日を含む直近7日分
- Claude Code と Codex の両方を送る。`--ai` の AI だけに絞らない。片方の AI でしか提出しない人でも、両方のグラフが埋まる
- 記録のない日は送らない。0 を送ると、本当に使わなかった日と区別できない
- 送る記録が1件もなければ、`PATCH` を呼ばない。API は1件以上を求めている

### 読むファイル

| AI          | 読むファイル                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| Claude Code | `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/` の下の `*.jsonl`。サブエージェントの `subagents/*.jsonl` も含む |
| Codex       | `${CODEX_HOME:-~/.codex}/sessions/` と `archived_sessions/` の下の `rollout-*.jsonl`                        |

- 更新日時が範囲の始まり（日本時間の6日前の0時）より前のファイルは読まない。範囲の中の行が入っていないためだ
- Codex は再開したセッションを元のファイルに書き足す。そのため、日はディレクトリの日付ではなく、行の時刻で決める
- Codex が圧縮した古い記録（`.jsonl.zst`）は読まない。Codex が圧縮するのは7日以上前に更新したファイルだけで、更新日時もそのまま残るので、いつも範囲の外になる。Codex がもっと早く圧縮するようになったら読む

### 行の読み方

日付は行の `timestamp`（UTC）に9時間を足した日本時間の日付にする。

| 項目                                     | Claude Code                                         | Codex                                                               |
| ---------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------- |
| 読む行                                   | `type` が `assistant` で、`message.usage` がある    | `type` が `token_usage_record`                                      |
| 重複の除き方                             | `message.id` と `requestId` の組が同じ行は1つにする | `payload.response_id` が同じ行は1つにする                           |
| 入力（`inputTokens`）                    | `input_tokens`                                      | `input_tokens` − `cached_input_tokens` − `cache_write_input_tokens` |
| キャッシュ書き込み（`cacheWriteTokens`） | `cache_creation_input_tokens`（ないときは 0）       | `cache_write_input_tokens`                                          |
| キャッシュ読み込み（`cacheReadTokens`）  | `cache_read_input_tokens`（ないときは 0）           | `cached_input_tokens`                                               |
| 出力（`outputTokens`）                   | `output_tokens`                                     | `output_tokens`。reasoning の分を含む                               |

- 重複は読んだファイルすべてを通して除く。同じ組の時刻が0時をまたぐときは、いちばん早い時刻の日にする
- Claude Code は1つの応答を何行かに分けて書き、どの行にも同じ usage を入れる。重複を除かないと、出力が約2.5倍になる（#9）
- Codex の `input_tokens` はキャッシュの分を含むので、それを引いて Claude Code とそろえる
- 古い Codex の記録には `token_usage_record` がないので、数えない

### 読めなかったとき

| 起きたこと                               | どうするか                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------- |
| AI のディレクトリがない                  | その AI は使っていないとみなし、送らない                                         |
| ファイルを1つでも開けない                | その AI の分は全部送らない。一部だけ送ると少なく出て、正しい値を上書きしてしまう |
| 行が JSON として読めない、要る項目がない | その行を飛ばす（[システム構成](architecture.md) の6章）                          |

## 5. 出力とエラー

### 出力の形

結果は日本語の文で標準出力に出す。読むのは AI なので、JSON にはしない。

- 絵日記の結果と消費トークン量の結果を、1行ずつ出す
- 失敗したときは、「次にすること」の1行を足す
- 通信の前に断ったときは、理由の1行と「次にすること」だけを出す
- 失敗の理由も標準出力に出す。行の順番が入れかわらないようにするためだ

```console
$ enikki submit --ai claude_code --image ./enikki.svg --text-file ./enikki.txt
絵日記：2026-11-10 の絵日記を出しました
消費トークン量：Claude Code と Codex の直近7日分を送りました
```

```console
$ enikki submit --ai claude_code --image ./enikki.svg --text-file ./enikki.txt
絵日記：出せませんでした。2026-11-10 の絵日記には、もうハンコが押されています
消費トークン量：Claude Code と Codex の直近7日分を送りました
次にすること：送り直さずに、この結果を利用者に伝えてください
```

| 終了コード | 意味                                                               |
| ---------- | ------------------------------------------------------------------ |
| `0`        | 絵日記を出し、消費トークン量も送れた。送る記録がなかったときも含む |
| `1`        | それ以外。記録を読めなかった AI があるときも `1` にする            |

### 「次にすること」

AI がすることは、利用者に頼む、直して出し直す、送り直さずに利用者に伝える、の3つに分かれる。CLI はレスポンスの `type` でエラーを見分ける（[API の設計](api-design.md) の4章）。

| 起きたこと                                                                    | 次にすること                                                                    |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| API キーがない、`missing-api-key`、`invalid-api-key`                          | 利用者に、ターミナルで `enikki login` を打ってもらう                            |
| ファイルがない、`--ai` の値が違う                                             | コマンドを直して、出し直す                                                      |
| 絵を変換できない、5 MB を超える、`invalid-image`、`image-too-large`           | 絵を描き直して、出し直す                                                        |
| 文章が空、`invalid-text`                                                      | 文章を直して、出し直す                                                          |
| `400`、`unknown-ai-type`、`invalid-token-usages`、知らない `type`             | 送り直さずに結果を利用者に伝え、`npm i -g enikki-cli@latest` で更新するよう頼む |
| `enikki-stamped`、つながらない、`5xx`、期限が過ぎた、記録を読めない AI がある | 送り直さずに、結果を利用者に伝える                                              |

- 「次にすること」は1行だけ出す。2つ以上に当たるときは、表の上の行を選ぶ。たとえば、絵日記が `invalid-image` で、消費トークン量が `5xx` なら、絵を描き直して出し直す。出し直せば、消費トークン量も送り直される
- つながらないときと `5xx` のときは、3回送ったあとの結果で決める
- 断られたときは、レスポンスの `detail` も出す。`invalid-text` なら、文章が空なのか長すぎるのかがわかる
- 消費トークン量の行には送れた AI、記録を読めなかった AI、送れなかった理由を書く
- 成功したら、`201` は「出しました」、`200` は「書きかえました」と出す。ただし、送り直したあとの `200` は「出しました」にする。前の回でサーバーが書き終えていれば、初めての提出でも `200` が返るためだ
- API キーはどの出力にも出さない

## 6. 配布と更新

```bash
npm i -g enikki-cli       # 入れる
enikki login              # API キーを設定する
enikki install-skill      # skill を入れる

npm i -g enikki-cli@latest && enikki install-skill   # 更新する
```

- 更新したら `enikki install-skill` も打ち直し、skill を新しくする
- 新しいバージョンを知らせる仕組みは作らない。古い CLI からの提出も API が受け付ける（[API の設計](api-design.md) の6章）
- sharp は OS ごとにビルド済みのものが npm から入るので、利用者のマシンではビルドしない
- npm への公開の手順は #13 で決める

## 7. AI に渡す skill

### 置き場所

| AI          | リポジトリの中                      | `enikki install-skill` が入れる先                |
| ----------- | ----------------------------------- | ------------------------------------------------ |
| Claude Code | `cli/claude/skills/enikki/SKILL.md` | `${CLAUDE_CONFIG_DIR:-~/.claude}/skills/enikki/` |
| Codex       | `cli/codex/skills/enikki/SKILL.md`  | `~/.agents/skills/enikki/`                       |

- skill は npm のパッケージに入れて配る
- `enikki install-skill` は、使っている AI にだけ skill をコピーする。`${CLAUDE_CONFIG_DIR:-~/.claude}` があれば Claude Code を、`${CODEX_HOME:-~/.codex}` があれば Codex を使っているとみなす。4章と同じ環境変数を見る
- 前に入れた skill は上書きする。ただし、入れる先がシンボリックリンクなら断る。リンクの先がもう一方の AI の skill だと、2つの skill が同じ場所に入り、あとに入れたほうだけが残るためだ
- リンクではなくコピーにする。CLI を消したときに、行き先のないリンクが残らない

### 中身

| 項目         | 書くこと                                                                                         |
| ------------ | ------------------------------------------------------------------------------------------------ |
| いつ使うか   | 利用者が今日の絵日記を頼んだとき                                                                 |
| 文章         | その日の会話から、AI の目線で書く                                                                |
| 絵           | 描き方は #21 に沿う                                                                              |
| ファイル     | 絵と文章は一時ディレクトリに書く。利用者のリポジトリには置かない                                 |
| 提出         | `enikki submit --ai <AI の種類> --image <絵> --text-file <文章>` を実行する                      |
| 待ち方       | 結果が出る前にコマンドが返ってきたら、終わるまで待って結果を読む。出し直さない                   |
| 結果         | 終了コードが `1` なら、「次にすること」のとおりにする。自分で送り直さない                        |
| 見つからない | `enikki` が見つからなければ、自分で入れずに利用者に伝える                                        |
| しないこと   | `enikki login` を実行しない。`~/.config/enikki/config.json` を読まない。API キーを会話に書かない |

AI によって違うところは次のとおり。

| 項目                 | Claude Code                                      | Codex                                                                                       |
| -------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 絵                   | SVG を書く                                       | `image_gen` が使えれば使い、使えなければ SVG を書く                                         |
| `image_gen` の絵     | なし                                             | 保存された場所（`$CODEX_HOME/generated_images/`）の PNG のパスを、そのまま `--image` に渡す |
| 待つ時間             | 3分にする                                        | `yield_time_ms` を 30000 にする                                                             |
| 途中で返ってきたとき | バックグラウンドに移ったら、出力のファイルを読む | session ID が返ったら、`write_stdin` で待つ                                                 |
| 通信                 | なし                                             | 最初から通信の許可を求める。既定のサンドボックスは外への通信を止めるためだ（#21）           |

- `enikki` が見つからないのは、たとえば Node.js のバージョンを切り替える道具を使っていて、ほかのプロジェクトで動かしたとき

## 8. ほかの設計との関係

| 設計                               | 合わせたこと                                                                                                                                                                                                                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [API の設計](api-design.md)（#16） | 絵はいつも WebP にして送る。`User-Agent: enikki-cli/<バージョン>` を付ける。`usages` は14件まで（7日 × 2つの AI）で、0件なら `PATCH` を呼ばない。レスポンスの知らないキーは無視する                                                                                                                         |
| 絵の作り方の調査（#21）            | サーバーは SVG を受け取らないので、CLI が WebP にする。#21 と違うところは2つある。#21 ではサーバーが PNG と JPEG も受け取る案だったが、#16 で WebP だけにした。CLI はいつも WebP を送るので食い違わない。また、`image_gen` の PNG は作業ディレクトリにコピーせず、保存された場所のパスをそのまま渡す（7章） |
| 消費トークン量の調査（#9）         | 4章の読み方、重複の除き方、直近7日分を送ること、0 を送らないことは #9 に沿う                                                                                                                                                                                                                                |

## 9. 確かめていないこと

- npm で `enikki-cli` という名前が空いているか
- Codex のサンドボックスの中で、skill どおりに待って提出できるか。PR #33 のレビューで Codex のソースを読んだかぎりでは、ディスク全体を読め、作業ディレクトリと一時ディレクトリに書け、外への通信は止まる
- Claude Code が `~/.agents/skills` も読むか。Claude Code の文書には書かれていない。読むなら、Codex 用の skill も Claude Code に見えてしまう
- sharp で、日本語の文字を含む SVG をきれいに描けるか（#21）
- Claude Code の記録には、タイトルの生成などの補助的なリクエストが入らない。手元の1セッションでは出力で約4%、キャッシュ読み込みで約23%少なかった（#9）
