# 開発環境と起動手順

手元でこのアプリを動かすための手順をまとめる。1章から5章は作業の手順で、6章から先は決めた理由と残っている確認事項だ。全体の構成は [システム構成](architecture.md) に書いてある。

2章のうち、Vite+ を入れて依存を入れ、起動するところまでは 2026-11-15 に実際に動かして確かめた。それ以外は void 1.9.1 と Vite+ 1.6.0 の文書を読んで書いた。

## 1. 使うもの

| 道具          | バージョン | 書いてある場所                              |
| ------------- | ---------- | ------------------------------------------- |
| Node.js       | 26.13.1    | `.node-version`                             |
| pnpm          | 12.21.0    | ルートの `package.json` の `packageManager` |
| Vite+（`vp`） | 1.7.0      | `pnpm-workspace.yaml` の `catalog`          |
| void          | 1.9.1      | `web/package.json`                          |

自分で入れるのは Vite+ だけでよい。Node.js と pnpm は、Vite+ が上のファイルを読んで自動で入れる。

## 2. はじめてのセットアップ

クローンした直後のマシンで行う。

1. Vite+ を入れる。入れたら、新しいターミナルを開く。

   ```sh
   curl -fsSL https://vite.plus | bash
   ```

2. リポジトリのルートで依存を入れる。

   ```sh
   vp install
   ```

3. `web/.env` を作り、手元用の OAuth アプリの値を書く（3章）。

4. `web/` で値が足りているかを確かめ、表を作り、起動する。

   ```sh
   cd web
   vpx void env check
   vpx void db migrate
   vp dev
   ```

`http://localhost:5173` を開いて画面が出れば、セットアップは終わりだ。

### うまくいかないとき

| 起きること                                    | 原因と直し方                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `vp` が見つからない                           | Vite+ を入れる前から開いていたターミナルを使っている。新しいターミナルを開く                                             |
| `Node.js 24.22+ or 26.12+ is required` と出る | nvm などが入れた古い Node.js が使われている。新しいターミナルを開く。直らなければ、コマンドの前に `vp env exec` を付ける |
| ポートが使われていて起動しない                | ポートは 5173 に固定してある。5173 を使っているほかのプロセスを止める                                                    |

## 3. 環境変数

手元の値は `web/.env` に書く。このファイルはコミットしない。

| 名前                                                 | 中身                   | 手元       | 本番                            |
| ---------------------------------------------------- | ---------------------- | ---------- | ------------------------------- |
| `AUTH_GITHUB_CLIENT_ID`、`AUTH_GITHUB_CLIENT_SECRET` | GitHub が発行する      | `web/.env` | `void secret put`               |
| `AUTH_GOOGLE_CLIENT_ID`、`AUTH_GOOGLE_CLIENT_SECRET` | Google が発行する      | `web/.env` | `void secret put`               |
| `BETTER_AUTH_SECRET`                                 | セッションの署名に使う | 要らない   | void が最初のデプロイで作る     |
| `CLOUDFLARE_API_TOKEN`                               | デプロイに使う         | 要らない   | GitHub Actions の secret（#13） |

- void が読むのは `web/.env` だけで、`.env.local` や `.env.example` は読まない
- 要る値の名前と型は `web/env.ts` に書いてコミットする
- OAuth アプリは、GitHub と Google のそれぞれに手元用と本番用を作る。合わせて4つになる
- Google の変数の名前は void の文書に例がなく、GitHub の名前の規則から当てはめた

## 4. ふだん使うコマンド

| すること                                  | コマンド                   | 打つ場所 |
| ----------------------------------------- | -------------------------- | -------- |
| 開発用のサーバーを起動する                | `vp dev`                   | `web/`   |
| フォーマット、lint、型チェック            | `vp check --deny-warnings` | ルート   |
| フォーマットし、lint の安全な修正をかける | `vp check --fix`           | ルート   |
| テスト                                    | `vp test`                  | `web/`   |
| ビルド                                    | `vp build`                 | `web/`   |
| void のコマンドを使う                     | `vpx void …`               | `web/`   |
| 依存を入れ直す                            | `vp install`               | ルート   |

PR の前に手元で回す検証と CI が回す検証は、同じコマンドにする。手元で通ったものが CI で落ちることを減らすためだ。lint とフォーマットの中身は [Lint と整形](lint-and-format.md) に書いた。テストの中身は #18 で、CI の組み方は #13 で決める。

## 5. 手元で通しで確かめる

変更は本番にだけデプロイするので、出す前に手元で次の順に確かめる。

1. `vp dev` でサーバーを起動する
2. 手元用の OAuth アプリでログインする
3. `/api-key` の画面で API キーを作る
4. 手元でビルドした `enikki` で提出する
5. ホームと絵日記の画面で確かめる

4では、`enikki login` と `enikki submit` に次の2つの環境変数を付ける。

| 環境変数          | 値                      | 付けないと起きること                                                           |
| ----------------- | ----------------------- | ------------------------------------------------------------------------------ |
| `ENIKKI_API_URL`  | `http://localhost:5173` | CLI が本番へ送る。手元のサーバーには何も届かない                               |
| `XDG_CONFIG_HOME` | `cli/.dev-config/`      | `enikki login` が `~/.config/enikki/config.json` の本番の API キーを上書きする |

- 2つの環境変数はシェルの設定ファイルに書かず、コマンドの前にその都度付ける。設定ファイルに書くと、ふだんの提出まで手元のサーバーへ送られる
- 付け忘れないように、2つを付けて手元の `enikki` を呼ぶスクリプトを `cli/package.json` に1つ置く

### 過去の日付の絵日記

CLI から出せるのは今日の絵日記だけだ。絵日記の日付はサーバーが決めるためで、この決まりは開発のためにも緩めない。

過去の日付の絵日記は、開発専用の画面のボタンで入れる。ボタンを押すと、ログインしている利用者に過去2週間分の絵日記と消費トークン量が入る。ハンコを押した日、押していない日、絵日記のない日を混ぜる。絵は、リポジトリに置いた同じ1枚をどの日にも使う。

void は名前が `.dev.ts` や `.dev.tsx` で終わる画面とルートを本番のビルドに入れないので、この画面は本番には出ない。

## 6. 決めたことと理由

| 決めたこと                                                                     | 理由                                                                                                                                                               |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 開発の Node.js は最新の LTS の 26 にする                                       | サポートが 2029年4月30日まで続く。void 1.9.1 は、24.22 以上の 24 か 26.12 以上でしか動かない                                                                       |
| Node.js と pnpm のバージョンは `26.13.1` のように最後の桁まで書く              | `26` と書くと、CI は新しいバージョンが出た日からそのバージョンで動き、手元は入れたときのまま残る。コードを変えていないのに CI だけが落ち、原因に気づきにくい       |
| CLI が動く Node.js は 24 以上にする                                            | 22 のサポートが 2027年4月30日に終わる。24 は 2028年4月30日まで続く                                                                                                 |
| `cli/` の `@types/node` を 24 のものにする                                     | 開発は 26 でするので、24 にない関数を書いても手元では動く。型チェックで、書いた時点で気づけるようにする                                                            |
| CI で CLI のテストを Node.js 24 でも動かす                                     | 同じ関数の動きが 24 と 26 で違うことは、型チェックでは気づけない                                                                                                   |
| void は `^` を付けずに書き、Vite+ は `pnpm-workspace.yaml` の `catalog` に書く | void は本番の動きを左右するので固定する。Vite+ は、`vp migrate` で上げたときに書かれる形に合わせる                                                                 |
| OAuth アプリを手元用と本番用に分ける                                           | GitHub の OAuth アプリには、送り返す先の URL を1つしか登録できない。分けておけば、手元の `web/.env` の値が漏れても本番のログインに関わらない                       |
| ポートを 5173 に固定する                                                       | OAuth の送り返し先と `ENIKKI_API_URL` が 5173 を前提にしている                                                                                                     |
| 過去の日付のデータは開発専用の画面から入れる                                   | `void db seed` は手元の D1 を空にするので、ログインで作った利用者と API キーが消える。SQL を流す方法では R2 に絵を置けない。本番を写す方法は、公開の前には使えない |
| `web/void.lock.json` はコミットしない                                          | Cloudflare のアカウント ID が入っていて、このリポジトリは公開だ。コミットするかは #13 で決める                                                                     |
| void の AI 向けの skill を pnpm で許可する                                     | `pnpm-workspace.yaml` の `permissions` に書いてある。依存を入れると、pnpm が `.claude/skills/` にリンクを作る                                                      |

Node.js、pnpm、Vite+ を上げるときは、void と同じく1つの PR で上げ、5章の手順を通してからデプロイする（[システム構成](architecture.md) の6章）。

Vite+ はルートで次のコマンドを打って上げる。`1.7.0` は、上げる先のバージョンに置き換える。`vite-plus` のバージョンと、`vite` の別名の先のバージョンを、migrate がまとめて書き換える。`--no-hooks` などを付けないと、git のフック、AI 向けの指示のファイル、エディタの設定まで作られる。

```sh
pnpm dlx --package=vite-plus@1.7.0 vp migrate --no-interactive --no-hooks --no-agent --no-editor
```

## 7. git に入れないもの

| ファイル                   | 中身                                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| `web/.env`                 | 手元用の OAuth アプリの値                                             |
| `web/.void/`               | void が作る型と、手元の D1 と R2 のデータ。消すと手元のデータも消える |
| `web/void.lock.json`       | Cloudflare のアカウント ID                                            |
| `cli/.dev-config/`         | 手元のサーバー用の API キー                                           |
| `node_modules/`            | 依存の実体                                                            |
| `.claude/skills/` のリンク | void の skill。pnpm が作り直す                                        |

## 8. ほかの Issue に渡すこと

CI の設計（#13）

- `.node-version` のバージョンで動かす
- 依存は `vp install --frozen-lockfile` で入れ、ロックファイルと違うバージョンが入らないようにする
- 4章のコマンドを呼ぶ
- CLI のテストを Node.js 24 でも動かす
- ビルドした結果に、5章の開発専用の画面が入っていないことを確かめる
- `void init` が作ったデプロイのワークフローの扱いを決める。いまは `web/.github/` に残してある。GitHub はルートの `.github/` しか読まないので、この場所では動かない
- `web/void.lock.json` をコミットするかを決める

Lint とフォーマット（#14）とテスト（#18）

- `vp check` と `vp test` の中身を決める
- D1 や R2 を使うコードのテストの書き方を決める。void のテストは Node.js の上で動き、Worker も手元のマイグレーションも使わない

## 9. まだ確かめていないこと

- クローンした直後のマシンで、2章の手順が通るか。今回確かめたのは、プロジェクトを作ったマシンの上だけだ
- nvm、mise、Vite+ の3つが入っているマシンで、新しいターミナルの `node` がいつも Vite+ のものになるか
- OAuth アプリに登録する送り返し先の URL。Better Auth の既定は `/api/auth/callback/github` と `/api/auth/callback/google` だが、void の文書には書かれていない
- `AUTH_GITHUB_CLIENT_ID` などを `web/env.ts` にも書く必要があるか
- 開発専用の画面と、対になる `.server.ts` の名前の付け方
- 開発用のサーバーが、起動のときにアプリの表も作るか。作るなら2章の `vpx void db migrate` は要らない
- 別のマシンで依存を入れたときに、pnpm が `.claude/skills/` に void の skill のリンクを作るか
- ひな形に入っている見本の表（`messages`）とマイグレーションを、最初のデプロイの前に [DB の設計](db-design.md) の表に置き換える

## 10. 今回はやらないこと

- 本番の D1 と R2 を手元から読むこと、本番のデータを手元に写すこと
- Docker や devcontainer で環境をそろえること
- Windows で開発すること
- Lint、フォーマット、テストの中身と、CI の組み方（#13、#14、#18）
